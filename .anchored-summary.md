## 3. Codebase Architecture

### VRTrackingApp.Web (Primary Application)
**Framework:** ASP.NET Core 10.0 MVC  
**Authentication:** Windows Integrated Auth (Active Directory/Kerberos) via IIS, with a dev-mode fallback that injects a "Local Developer / Admin" identity  
**Database:** EF Core with InMemory provider by default (demo/seeded data); SQL Server in production (controlled by `ConnectionStrings:UseInMemory` setting)  
**DI / Services:**

- `ScanImportService` — Handles file upload processing (CSV/PDF/Nessus formats)
- `ScanIngestionService` — Nessus XML/CSV ingestion engine with multi-level deduplication
- `NessusXmlParser` — Parses Nessus scan files into normalized domain objects
- `ScanIngestionService` + `ScanIngestionLock` (DB-backed pessimistic lock) + in-process `SemaphoreSlim` — Concurrency control for scan ingestion
- **MSRC Integration:** `MsrcService`, `VulnerabilityEnrichmentService`, `MsrcSyncBackgroundService` (background sync of Microsoft security advisories)
- **NVD Integration:** `NvdService`, `NvdEnrichmentService`, `NvdSyncBackgroundService` (background sync of NVD CVE data)
- **Remediation Engine:** `RemediationEngine`, `RemediationBackgroundService`, `RemediationQueue`, `IRemediationProvider` (3 implementations: `SimulatedRemediationProvider`, `WinRmWindowsUpdateProvider`, `LinuxSshRemediationProvider`)
- **Exception Module V2:** `ExceptionRoutingService`, `ExceptionWorkflowService`, `ExceptionLifecycleService`, `ExceptionLifecycleHostedService` (background exception lifecycle management), `RiskMatrixService`
- **Notifications:** `NotificationService`, `UserNotificationService`, `EmailChannel` (optional SMTP-based), `EmailTemplateService`, `NotificationViewComponent`
- `DomainRoleClaimsTransformation` — Maps Windows-authenticated users to DB `UserAccount` records and attaches role claims
- `DbSeeder` — Seeds demo data (18 hosts, 130 findings, 3 scan cycles: January Monthly, Feb Patch Tuesday, Q1 Risk-Based)

**Controllers (13):** Dashboard, Home, Account, Admin, Asset, Audit, Exceptions, Health, Hosts, Lifecycle, Notification, Reports, Scans, Search, Upload, Vulnerabilities

### VRTrackingApp.API (Secondary REST API)
**Framework:** ASP.NET Core 10.0 with Controllers  
**Architecture:** Clean CQRS using MediatR — every endpoint delegates to a query or command handler  
**Dependencies:** AutoMapper (profiles), MediatR (14.2.0), EF Core SqlServer (10.0.9), Swagger/OpenAPI, Swashbuckle  
**Swagger UI** enabled in Development  
**Migration auto-apply** on startup (`dbContext.Database.Migrate()`)  
**File Upload:** `FileUploadService` with settings for max size (100MB), allowed extensions (.csv, .pdf)

**CQRS Feature Structure:**
- **Assets:** 6 commands (Create/Update/Delete + 6 queries) — GetAssets, GetAssetById, GetByScanId, GetByHostName, GetByIpAddress
- **AssetVulnerabilities:** 5 commands, 6 queries
- **Scans:** 5 commands, 5 queries
- **Vulnerabilities:** 4 commands, 6 queries (GetBySeverity, GetByCve, GetById)
- **References:** 5 commands, 6 queries
- Each query/command has a handler that calls the appropriate repository + AutoMapper to map to DTOs

### Infrastructure Layer (API-side)

- **Specialized Repositories:** `AssetRepository`, `VulnerabilityRepository`, `ScanRepository`, `AssetVulnerabilityRepository`, `ReferenceRepository`
- **Specification Pattern:** `ISpecification<T>`, `BaseSpecification<T>`, `SpecificationEvaluator<T>` — supports criteria, includes, ordering, paging
- **DI Registration:** `InfrastructureServiceCollectionExtensions.AddInfrastructureServices()` — registers `ApplicationDbContext` (SQL Server) + all repositories + base generic repo

### Key Technical Decisions in the Code
1. **Two-layer split:** The API uses a simpler domain model (`VRTrackingApp.Domain`), while the Web app uses a much richer model (`src/VRTrackingApp.Data`). They are NOT shared — the API does not reference `src/VRTrackingApp.Data`, and the Web app does not use `VRTrackingApp.Domain`/`VRTrackingApp.Infrastructure`.

2. **InMemory by default:** The Web app defaults to EF Core InMemory for zero-dependency local/demo runs, seeded with `DbSeeder`. SQL Server is used in production. The API always uses SQL Server.

3. **Design-time factory:** `DesignTimeDbContextFactory` in `src/VRTrackingApp.Data` allows `dotnet ef migrations` to target SQL Server at design time regardless of runtime provider.

4. **Exception module V2:** Uses a multi-stage approval workflow with risk matrix, enum-to-string conversions for readability, and extensive navigation properties. Includes evidence uploads, vendor responses, ticketing system links, and comment trails.

5. **Scan deduplication:** Three-tier approach:
   - File-level: SHA-256/MD5 hash comparison (Scenario 3)
   - Scan-level: Nessus UUID or composite key (Scenario 4)
   - Finding-level: PluginId|Host|Port|Protocol composite key with New/Duplicate/Reopened/Updated/Remediated decisions (Scenarios 5-13)

6. **Remediation providers:** Runtime-selected via `Remediation:Mode` config ("Simulated" default, "Live" for WinRM/SSH). Multiple `IRemediationProvider` registrations in DI.

7. **`.slnx` format:** Modern .NET solution file format (not legacy `.sln`).
